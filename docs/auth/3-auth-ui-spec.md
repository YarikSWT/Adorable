# Спецификация: UI авторизации и multi-tenancy

**Документ 3 из 3 — UI-спецификация**

Этот документ описывает интерфейс пользователя для всего, что появляется в системе из Документов 1 (модель данных и flows) и 2 (бэкенд: API, Better Auth, Drizzle). Ни строчки кода — только что должно быть на экране, как пользователь между этими экранами движется, какие состояния и ошибки он видит.

UI-вопросы чата, превью, билд-статуса и всего, что относится к самой работе с проектом, — за рамками этого документа. Они либо уже работают в текущем форке, либо описаны в отдельных спеках.

---

## 1. Контекст и принципы

### 1.1. Что есть сейчас

Текущий форк — однопользовательское приложение с двумя основными экранами:

- **Home** (`/`) — список созданных проектов (grid карточек) и форма «опиши идею» для создания нового. Никакой авторизации, никакого профиля.
- **Workspace** (`/[repoId]`) — двухпанельный экран: слева чат с AI, справа iframe превью. Никаких настроек проекта, никаких member-ов.

Заголовок (header) минимальный: лого + переключатель темы.

UI собран на Next.js App Router + React 19 + Tailwind CSS 4 + shadcn/ui (Radix-компоненты). Этот стек сохраняется.

### 1.2. Что нужно добавить

После внедрения авторизации (Документы 1 и 2) пользовательский путь становится таким:

1. Незалогиненный юзер заходит на `/` → видит лендинг или редирект на `/login`.
2. Регистрируется, подтверждает email, получает персональную организацию.
3. Создаёт проект (как сейчас), но теперь проект привязан к его организации.
4. Может создать team-организацию, добавить туда проект, пригласить других людей (UI приглашений — не в этой спеке, см. 1.4).
5. Может настроить публикацию, выпустить API-токены, посмотреть свой usage и лимиты.
6. Если у юзера есть admin-роль — может зайти в минимальную консоль администратора (опционально, см. 9).

### 1.3. Принципы UI

- **Server-side по умолчанию.** Каждая страница — server component с актуальными данными на момент рендера. Клиентский state используем только там, где без него не обойтись (формы, диалоги, переключатели).
- **Отдельные страницы вместо модалок там, где это разумно.** Создание проекта, настройки членов, выпуск токена — отдельные URL. Это даёт shareable links, понятную историю в браузере и упрощает доступность (a11y). Модалки оставляем только для подтверждений необратимых действий (delete project, revoke token) и для одноразовых показов секретов (см. 6.5).
- **Минимум JavaScript-стейта.** Формы submit'ятся через Server Actions или прямой POST на API. Loading-состояния — через Next.js `loading.tsx`/Suspense, не через локальные `isLoading`-флаги.
- **Skeleton, не spinner.** Где есть осмысленный layout (карточки проектов, таблицы) — показываем скелет, а не крутилку. Это снижает воспринимаемую задержку.
- **Inline-валидация + summary.** В формах ошибки показываются под конкретным полем, плюс одно общее сообщение сверху для серверных ошибок (квота превышена, конфликт email).
- **Ясные пустые состояния.** «Нет проектов» ≠ пустая страница. Каждый список с возможностью быть пустым имеет иллюстрацию + объяснение + основное действие.
- **Заглушки скрываем, а не показываем «coming soon».** Если фича не реализована (приглашения, кастомные домены, реферальная программа) — её UI **не отображается**, а не показывается с лейблом «скоро будет». Юзеры не любят неактивные кнопки.
- **Совместимость с темой.** Поддерживаем light и dark, переключатель уже есть в текущем forke. Цветовая палитра — стандартная shadcn (`background`, `foreground`, `primary`, `muted`, `destructive`).
- **Адаптивность — desktop-first, но без поломок.** На mobile сайдбары превращаются в сворачиваемые меню, таблицы — в списки. Базовый brakepoint — 768px.

### 1.4. Что **не** делается в этом UI

Перечисленное ниже — структурно есть на бэкенде и в схеме (Документ 1, раздел 3 и 12), но в UI этой версии отсутствует:

- Принятие приглашения в организацию или проект — нет ни формы создания приглашения, ни landing-страницы для accept-токена.
- Реферальный код в форме регистрации.
- Привязка кастомного домена к проекту.
- Telegram и Max как кнопки OAuth-логина (только Google, Yandex, VK).
- Выход юзера из чужой организации.
- Полноценная админка с CRUD по всем сущностям (только минимальное read-only console, см. 9).
- Сменa юзером своего email (только через админку, см. Документ 2, 7.11).
- Редактирование `memory` проекта (это часть будущей спеки про чат).

## 3. Auth-страницы

### 3.1. Общий вид

Все auth-страницы (login, signup, forgot, reset, verify, error) делят общий **auth layout**: центрированная карточка ~400px шириной на нейтральном фоне, лого Adorable сверху, ссылка на смену темы внизу. Никакой навигации, никакого футера с тяжёлыми ссылками — фокус только на форме.

### 3.2. Login (`/login`)

**Содержимое:**
- Заголовок: «Войти в Adorable».
- Кнопки OAuth (приоритет — потому что это быстрее): «Войти через Google», «Войти через Yandex», «Войти через VK». Каждая — с иконкой провайдера, full-width, в один столбец.
- Разделитель «или».
- Поля: email, пароль.
- Под паролем — линк «Забыли пароль?» вправо.
- Кнопка «Войти» (primary, full-width).
- Под формой — «Нет аккаунта? Зарегистрироваться» (ссылка на `/signup`).

**Поведение:**
- Email валидируется на формат при blur.
- Пароль — минимум 8 символов (см. Документ 2, 3.1), валидация только на сервере, на клиенте просто required.
- Submit → POST `/api/auth/sign-in/email` (Better Auth).
  - 200 → редирект на `?from=` или на `/`.
  - 400 (неверный пароль или email) → общая ошибка под формой: «Неверный email или пароль» (не раскрываем — что именно). Поля очищать **не нужно** (только пароль).
  - 423 (юзер `suspended`/`deleted`) → «Аккаунт временно недоступен. Свяжитесь с поддержкой».
  - 429 (rate limit) → «Слишком много попыток входа. Попробуйте через минуту».
- Кнопка OAuth → редирект на провайдера → callback → редирект сюда же или на `/`.

**Состояние «уже залогинен»**: если юзер заходит на `/login` с активной сессией — редирект на `/`.

### 3.3. Signup (`/signup`)

**Содержимое:**
- Заголовок: «Создать аккаунт».
- Те же три кнопки OAuth.
- Разделитель «или».
- Поля: имя, email, пароль.
- Чекбокс «Я согласен с условиями использования и политикой конфиденциальности» (ссылки — на отдельные публичные страницы; их подготовка — за рамками технической спеки, но плейсхолдеры обязательны).
- Кнопка «Зарегистрироваться» (primary, full-width).
- «Уже есть аккаунт? Войти» (ссылка на `/login`).

**Поле реферального кода — отсутствует.** Это явное решение из Документа 2, правка 4.

**Поведение:**
- Email нормализуется на сервере (Документ 2, 3.2). UI не показывает нормализованный вариант, в форме остаётся то, что ввёл юзер.
- Пароль — индикатор силы под полем (короткий/нормальный/сильный — на основе длины и набора символов). Это UX-bonus, не блокирует submit.
- Submit → POST `/api/auth/sign-up/email`.
  - 200 → редирект на `/verify-email?pending=true` с подсказкой «проверьте почту» (см. 3.5).
  - 422 (валидация: слабый пароль, неверный email) → ошибка под полем.
  - 409 (email уже занят) → **общая** ошибка «Не удалось зарегистрироваться. Возможно, у вас уже есть аккаунт — попробуйте войти». **Не раскрываем**, что email конкретно занят (защита от перебора, см. Документ 1, 4.1).
  - 429 (rate limit регистраций) → «Слишком много попыток. Попробуйте через час».

### 3.4. Forgot password (`/forgot-password`)

**Содержимое:**
- Заголовок: «Восстановление пароля».
- Поле email.
- Кнопка «Прислать ссылку».
- Ссылка «Назад ко входу».

**Поведение:**
- Submit → POST `/api/auth/forgot-password`.
- **Всегда** возвращаем юзеру одинаковое сообщение «Если такой email есть в системе — мы прислали ссылку для восстановления». Не раскрываем существование (Документ 1, 4.5).
- 429 → «Слишком много запросов. Попробуйте через час».

### 3.5. Reset password (`/reset-password?token=...`)

**Содержимое:**
- Заголовок: «Новый пароль».
- Поле «Новый пароль», поле «Повторите пароль».
- Кнопка «Сохранить».

**Поведение:**
- Без `?token=` или с истёкшим/использованным токеном — страница ошибки «Ссылка недействительна», кнопка «Запросить новую».
- Submit → POST `/api/auth/reset-password`.
- Успех → редирект на `/login` с тостом «Пароль обновлён. Войдите с новым паролем». Все активные сессии юзера на этот момент **уже инвалидированы** на бэкенде.

### 3.6. Verify email (`/verify-email`)

Эта страница работает в двух режимах:

**Режим 1 — `?pending=true`** (после signup): «Мы прислали письмо на `<email>`. Перейдите по ссылке, чтобы подтвердить адрес. Не пришло — проверьте папку «Спам» или [запросить заново]». Кнопка «запросить заново» — disabled на 30 секунд после клика, чтобы избежать спама.

**Режим 2 — `?token=...`** (после клика на ссылку из письма): автоматический POST на `/api/auth/verify-email` при загрузке страницы. Возможные исходы:
- Успех → «Email подтверждён», кнопка «К проектам» (редирект на `/`).
- Токен истёк / использован → «Ссылка не действительна. Запросите новое письмо», кнопка «Запросить новое».

### 3.7. Account conflict (`/auth/account-conflict?provider=google&email=...`)

Эта страница показывается, когда юзер пытается войти через OAuth, и существующий юзер с таким email уже есть, привязанный другим способом (см. Документ 1, 4.3).

**Содержимое:**
- Заголовок: «Аккаунт уже существует».
- Текст: «Похоже, у вас уже есть аккаунт с email `<email>`, привязанный через `<email-and-password / yandex / vk>`. Чтобы войти через `<google>`, сначала войдите старым способом и привяжите этого провайдера в настройках».
- Кнопка «Войти существующим способом» → `/login?email=<email>` (поле email предзаполнено).
- Дополнительная подсказка: «Не помните, как регистрировались? Восстановите доступ по email».

Эта страница защищает юзера от создания дублирующих аккаунтов и от непреднамеренного слияния. Не показывает «слить аккаунты сейчас» — потому что слияние требует доказательства владения обоими, а у юзера на руках только один.

### 3.8. OAuth error (`/auth/oauth-error?reason=...`)

Общая страница для случаев, когда callback не дошёл до целевого состояния: юзер отказал в провайдере, network ошибка, токен невалидный. Содержит короткое объяснение по `reason` и кнопку «Вернуться ко входу».

## 4. Шелл и навигация

### 4.1. Глобальный header

Появляется на всех авторизованных страницах. Слева направо:

- Лого Adorable (клик → `/`).
- **Org switcher** (см. 4.2) — показывается, **только если** у юзера больше одной организации. Иначе скрыт, потому что для single-org-юзеров (большинство) он бесполезный шум.
- Spacer.
- (Опционально) ссылка «Проекты», если есть осмысленный «не-проектный» дашборд орги.
- Меню юзера (см. 4.3).

### 4.2. Org switcher

Кнопка с текущим org-name + аватаром (инициалы или загруженная картинка). Клик открывает popover:

- Список всех организаций юзера (max 8 видимых, дальше скролл).
- Для каждой — название, slug мелким текстом, текущая роль («owner», «admin», «member»).
- Активная подсвечена.
- Внизу — «+ Создать организацию» (если у юзера есть пермишен; в первой версии — у всех залогиненных).

Переключение организации **меняет** сегмент URL (если юзер на org-странице) или **не меняет**, если он внутри проекта (потому что проект принадлежит конкретной org-е, переключаться вне её контекста некорректно).

Для юзеров с одной (личной) орг'ой свитчер скрыт совсем — они работают «прозрачно» в personal-org, вообще не видя её как сущность.

### 4.3. Меню юзера

Клик по аватару (правый верхний угол) → popover с пунктами:

- Имя юзера + email серым (обрезанный).
- «Профиль» → `/settings/profile`.
- «Безопасность» → `/settings/security`.
- «Подключения» → `/settings/connections`.
- — divider —
- «Биллинг» → `/orgs/<active-org>/billing` (если есть пермишен).
- — divider —
- «Админка» → `/admin` (только если `is_admin = true`).
- — divider —
- «Выйти» → POST `/api/auth/sign-out` → редирект на `/login`.

### 4.4. Project-level навигация

Внутри `/projects/<id>/...` слева появляется тонкий sidebar (collapsible на mobile):

- «Workspace» (текущий чат+превью).
- «Settings» — раскрывает подпункты:
  - General
  - Members
  - Tokens
  - Publication
  - Danger Zone

Active-state: текущий пункт подсвечен полосой слева.

Сверху над sidebar'ом — название проекта + dropdown-индикатор для быстрого переключения между проектами текущей org (отдельной страницы не требует, popover со списком).

### 4.5. Org-level навигация

Внутри `/orgs/<slug>/...` — горизонтальные табы под header'ом:

- Overview (если есть смысловой дашборд)
- Settings
- Members
- Billing

Тонкий sidebar здесь не нужен, страниц мало.

### 4.6. Email-not-verified баннер

Глобально, на всех авторизованных страницах, **если** у юзера `email_verified = false` — над основным контентом показывается dismiss-able баннер (warning-style):

> «Подтвердите email, чтобы создавать проекты и публиковать приложения. [Отправить письмо снова]»

Кнопка «Отправить письмо снова» disabled 30 секунд после клика. Dismiss кладётся в localStorage, но **возвращается** на следующий день — потому что это важно.

## 5. Настройки юзера

### 5.1. `/settings/profile`

- Блок «Аватар»: текущий + кнопка «Загрузить». В первой версии можно ограничиться **только инициалами по имени** и не делать upload, чтобы не возиться с медиа-хранилищем.
- Поле «Имя» + кнопка «Сохранить».
- Email — read-only поле с подсказкой «Email можно изменить только через поддержку» (см. Документ 2, 7.11 — смена через админку).

### 5.2. `/settings/security`

- **Сменить пароль**: текущий пароль, новый пароль, повторить. Submit → POST `/api/auth/change-password`. Успех → тост «Пароль обновлён». Это инвалидирует все сессии **кроме текущей** (Better Auth дефолтное поведение настраиваемо; принимаем «сохранить текущую сессию»).

- **Активные сессии**: таблица из `sessions` для текущего юзера. Колонки: устройство (по UA — «Chrome на macOS»), IP-адрес, последняя активность, создана. У текущей сессии — лейбл «Эта сессия» вместо кнопки. У остальных — кнопка «Завершить». Внизу — кнопка «Завершить все остальные сессии» (destructive, с подтверждением).

### 5.3. `/settings/connections`

Список OAuth-провайдеров (Google, Yandex, VK). Для каждого:

- Если привязан — иконка зелёной точки, текст «Привязан» + email из провайдера (если он отличается от основного — отдельная подсказка). Кнопка «Отвязать» (с подтверждением, **disabled** если у юзера нет пароля и это последний способ входа — нельзя оставить аккаунт без способа аутентификации).
- Если не привязан — кнопка «Привязать» → OAuth-флоу → callback → запись в `accounts` (Документ 1, 4.4).

Сверху короткое объяснение: «Один OAuth-аккаунт может быть привязан к одному пользователю Adorable. Если попробуете привязать аккаунт, который уже используется кем-то ещё — получите ошибку».

## 6. Проект — settings

### 6.1. Список проектов на home

`/` для залогиненного:

- Слева сверху — текст «Проекты» (size большой), справа — кнопка «+ Новый проект» (primary).
- Опционально — фильтры: org-switcher (если несколько org), search-input по имени.
- Сетка карточек проектов: имя, превью-thumbnail (если уже билдился — берём из preview-провайдера, иначе плейсхолдер), маленькие чипы с информацией (например, «published» / «private» / «not published»), последняя активность.
- Карточка кликабельна целиком → `/projects/<id>` (workspace).
- В правом верхнем углу карточки — иконка-меню (три точки): «Settings», «Archive», «Delete» (с подтверждением).

Пустое состояние (юзер только что зарегистрировался): иллюстрация + текст «Создайте первый проект — расскажите AI, что хотите построить» + большая кнопка «Создать проект».

### 6.2. `/projects/new`

В текущем форке создание проекта работает прямо с home (форма «опиши идею» сразу запускает агента). Сохраняем этот UX, но добавляем:

- Если у юзера несколько организаций — **dropdown «Организация»** перед текстарей. Default — текущая активная (из org switcher). Это важно: без явного выбора юзер может случайно создать проект в wrong org.
- Если у юзера превышен лимит `projects.max` — форма disabled, под ней объяснение «Достигнут лимит проектов в плане Free. [Перейти на платный] или [удалите старый проект]».

### 6.3. `/projects/<id>/settings` (general)

- Поля: имя проекта, описание (необязательно).
- **Slug** — read-only после первой публикации (`preview_subdomain_locked = true`), редактируемый до неё. Подсказка «slug фиксируется после первой публикации, чтобы preview-ссылки не ломались».
- Кнопка «Сохранить» (disabled если ничего не изменено).
- Раздел «Memory» — **скрыт в этой спеке** (часть будущей чат-спеки).

### 6.4. `/projects/<id>/settings/members`

Таблица члены проекта:

- Колонки: имя/email, роль (бейдж), origin («через организацию» / «явно»), действия.
- «Через организацию» — это юзеры, которые видят проект благодаря org-членству (без записи в `project_members`). Показываем их с эффективной ролью, но **редактировать роль нельзя** прямо тут — нужно либо изменить org-роль, либо «повысить» через явное добавление.
- «Явно» — записи из `project_members`. Можно изменить роль (dropdown с viewer/editor/publisher/owner), удалить (с подтверждением, если это owner — disabled, нужен второй owner или передача).

В верху страницы — кнопка «+ Добавить участника». В первой версии **открывает модалку с подсказкой**: «Приглашения участников появятся в следующей версии. Сейчас участники добавляются администратором через support». Это компромисс — Документ 1 явно оставляет UI приглашений «на потом», но кнопка выглядит логично, поэтому не убираем её, а ставим заглушку. (**Альтернатива** — убрать кнопку совсем; решение зависит от того, насколько часто в первой версии будут реально добавлять участников. По умолчанию — заглушка.)

### 6.5. `/projects/<id>/settings/tokens`

Таблица токенов:

- Колонки: имя, kind (бейдж: public/server/export), prefix (`pk_live_AbCdEf12...`), создан, last used, expires, статус (active/revoked/expired).
- Действия: «Отозвать» (с подтверждением).

Сверху — кнопка «Создать токен». Открывает **модалку**:

- Поля: имя, kind (radio с пояснением каждого), expiration (опционально).
- Submit → создание токена → **закрывается старая модалка, открывается новая «Токен создан»** с большим моноширинным текстом полного токена и кнопкой «Скопировать». Под ним красным предупреждение: «Это **единственный** раз, когда вы видите токен целиком. Сохраните его сейчас». Кнопка «Понятно, сохранил» закрывает модалку.

Это единственный кейс «одноразового показа секрета» в продукте (см. 1.3).

### 6.6. `/projects/<id>/settings/publication`

- Заголовок: «Публикация».
- Если ещё не публиковался: один блок-CTA с описанием «Опубликуйте, чтобы получить URL и поделиться» и кнопкой «Опубликовать» — открывает диалог выбора видимости (radio: private/authenticated/public с пояснением каждого), submit → POST promote → success → блок перерисовывается в «опубликовано».
- Если опубликован:
  - URL поддомена (clickable, copy-button рядом).
  - Текущая видимость (visible-pill) + кнопка «Изменить» (открывает диалог как при первой публикации, но с pre-selected текущим значением).
  - «Опубликовано: 5 минут назад» + «версия snapshot `<commit_hash>`».
  - Кнопка «Опубликовать снова» (повторно собирает текущий код проекта).
  - Раздел «Кастомный домен» — **скрыт в этой спеке** (структурно есть, UI отсутствует, см. Документ 1, 7.5).

Под публикацией — **информер**: «`authenticated`/`private` требуют от посетителей подтверждённого email. `public` доступен всем».

### 6.7. `/projects/<id>/settings/danger`

Только destructive-действия. Каждое — отдельный блок с обводкой destructive-цвета:

- **Архивировать**: «Проект перестанет быть видимым в списке, но его можно восстановить через поддержку. Sandbox освобождается, публикация остаётся доступной». Подтверждение: ввод имени проекта.
- **Удалить**: «Проект и его данные будут удалены безвозвратно». Подтверждение: ввод имени проекта **и** ввод текста «удалить».

Видны только юзерам с `project.delete` пермишеном.

## 7. Организация

### 7.1. Когда персональная org показывается отдельно

**Никогда** — для personal-org нет дашборда `/orgs/<slug>`, нет страницы members, нет настроек. Личные проекты юзера показываются прямо в `/`. Биллинг personal-org доступен через меню юзера → «Биллинг» (роутится на `/orgs/<personal-slug>/billing`).

Это решение — потому что показывать юзеру с одной personal-org что-то отдельное на уровне «организация» — лишний concept, который только запутает.

### 7.2. `/orgs/<slug>` — overview team-org

Видимо только для team-организаций. Содержит:

- Имя орги, тип (бейдж «team»), slug.
- Счётчики: проекты (active), участники, текущий план.
- Список последних 5 проектов (карточки как на home).
- Сводка по quota (см. 8) — миниатюрные прогресс-бары.

### 7.3. `/orgs/<slug>/settings`

- Имя, slug (slug редактируется, но с предупреждением «изменит URL орги»).
- Удалить орг — destructive, только для `organization.delete` (= owner).

### 7.4. `/orgs/<slug>/members`

Структурно как members проекта (6.4):

- Таблица членов с колонками имя/email, org-роль, действия.
- Кнопка «+ Добавить участника» — заглушка с тем же текстом «Приглашения появятся в следующей версии».
- Удаление участника (с подтверждением, последнего owner'а удалить нельзя).
- Изменение роли — dropdown.

### 7.5. `/orgs/new`

Простая форма:

- Имя.
- Slug (auto-generated из имени, можно отредактировать).
- Кнопка «Создать».
- Submit → POST `/api/orgs` → редирект на `/orgs/<slug>`.

После создания юзер становится org-owner.

## 8. Биллинг и квоты (UI-видимая часть)

### 8.1. `/orgs/<slug>/billing`

Видимо для `organization.billing.view` (org-owner и org-admin).

- **Текущий план**: карточка с именем плана, ценой, периодом «текущий период: с X по Y». Если план `free` — лейбл «Free» + текст «Триал бесплатно». Если другой — кнопка «Сменить план» (в первой версии **скрыта**, потому что реальные платежи не реализованы; см. Документ 1, 6.6).
- **Лимиты и использование**: таблица с колонками: ресурс (LLM tokens, image generations, STT minutes, ...), лимит, использовано, прогресс-бар, остаток. При приближении к 100% — цвет полосы становится оранжевым, при 100% — красным.
- **Override-ы**: если на org есть активный `plan_overrides` — show раздел «Индивидуальные лимиты» с подсказкой «Эти лимиты установлены поддержкой». Перечислены изменённые ресурсы и их новые значения.
- **Usage events**: ссылка-аккордеон «История событий» — открывает таблицу последних 50 `usage_events` (на отдельной странице или с pagination) с колонками: дата, kind, amount, model, project. Это даёт прозрачность, особенно важна в team-org (видно, кто из членов сколько потратил).

### 8.2. Inline-индикатор квоты на home/workspace

Когда юзер близок к лимиту (>80% по любому ресурсу) — показываем слабый inline-баннер на home «Вы используете 85% лимита токенов на этот месяц. [Подробнее]». Не агрессивный, dismiss'able, но возвращается раз в день.

### 8.3. 402 при превышении

Когда юзер пытается сделать что-то платное (отправить сообщение в чат, опубликовать, создать проект) и квоты не хватает — UI **не блокирует** действие на клиенте (иначе раскрываем лимит до того, как сервер его проверит), а показывает ответ сервера 402 как inline-сообщение в контексте действия:

- В чате: вместо отправки — bubble «Превышен лимит токенов на этот месяц. [Перейти на платный план]».
- В create project: «Превышен лимит проектов в плане. [Удалить старый] или [перейти на платный]».
- В publish: «Превышен лимит публикаций в этом периоде».

Текст ошибки берётся из `error.message`, ссылка-CTA генерируется UI'ем по `error.code`.

## 9. Админка (минимальная, опциональная)

В Документе 1 (раздел 9.1) сказано: в первой версии **UI админки не делается**, только защищённые API. Документ 2 (раздел 7.11) описывает API.

Мы оставляем **возможность** для очень минимального read-only Admin Console, чтобы базовые операции (посмотреть список юзеров, найти конкретного, посмотреть его org-и) не требовали curl. Но это **опциональный** элемент — если не успеем в первый релиз, ничего критичного не теряется.

Если делаем минимум:

### 9.1. `/admin`

- Дашборд: счётчики юзеров (всего, активных, за неделю), счётчик организаций, счётчик опубликованных проектов.
- Не больше — без сложных графиков.

### 9.2. `/admin/users`

- Таблица: email, имя, статус, дата регистрации, число организаций.
- Поиск по email и имени.
- Клик на строку → `/admin/users/<id>`.

### 9.3. `/admin/users/<id>`

- Профиль юзера (read-only).
- Список его организаций (с ролью в каждой).
- Действия (если есть пермишен): «Suspend», «Unsuspend», «Сбросить пароль» (отправляет letter), «Сменить email» (форма с input на новый email — это API из Правки 5 Документа 2).

### 9.4. `/admin/orgs/<id>`

- Профиль орги, текущий план, активная подписка.
- Лимиты + override (если есть, показываем что и кем установлено, кнопка «Удалить override»).
- Кнопка «+ Добавить override» — простая форма: ресурс (dropdown известных kind-ов), новое значение, причина (текстполе), expires-at (опционально).
- Список членов и проектов.

### 9.5. `/admin/audit`

- Таблица аудит-лога с фильтрами: actor, target_type, action, период.
- Бесконечная подгрузка вниз (или pagination — что проще).
- Колонки: время, actor, action, target, IP. Полный JSON metadata — раскрывается по клику на строку.

### 9.6. Что **не** делается в админке

- Создание/удаление юзеров (только бан).
- Создание новых ролей или редактирование пермишенов (только сидинг через миграции).
- Создание планов (только редактирование лимитов существующих).

## 10. Ошибки и пустые состояния

### 10.1. Стандартные ошибки

| Код | Где появляется | Что показываем |
|------|---------------|---------------|
| 401  | Любая защищённая страница без сессии | Редирект на `/login?from=<path>` |
| 403  | Защищённая страница, на которую у юзера нет пермишена | Страница «Нет доступа» (центрированная иллюстрация + текст + кнопка «Назад») |
| 404  | Несуществующий ресурс **или** ресурс, который мы не хотим раскрывать | Та же страница «Не найдено» — **одинаковая** для обоих случаев (Документ 1, 5.5) |
| 423  | Action требует verified email, а его нет | Inline-сообщение в форме + ссылка «Отправить письмо снова» |
| 402  | Quota exceeded | Inline в контексте действия (см. 8.3) |
| 429  | Rate limit | Тост «Слишком быстро, подождите» с `Retry-After` countdown |
| 5xx  | Server error | Generic «Что-то пошло не так. Попробуйте обновить страницу. Если повторится — напишите в поддержку» |

### 10.2. Пустые состояния

Каждый список с возможностью быть пустым имеет свою иллюстрацию + текст + действие:

- Нет проектов → «Создайте первый проект».
- Нет членов в org (только сам owner) → «Пригласите коллег» (заглушка).
- Нет токенов → «Создайте API-токен для интеграций».
- Нет аудит-событий за период → «За выбранный период событий нет».

### 10.3. Loading

- Список карточек / таблица → skeleton-карточки/строки.
- Заголовок страницы → пустое место (не shimmer).
- Submit формы → primary-кнопка превращается в spinner с disabled остальной формой, **не** замораживает страницу.

## 11. Уведомления (toasts)

Тосты — для эфемерных подтверждений. Появляются в правом нижнем углу, автодиспэп через 4 секунды, accessible (`role=status`).

Ситуации:

- Сохранение настроек («Сохранено»).
- Инвалидация сессии («Сессия завершена»).
- Копирование токена/URL в буфер («Скопировано»).
- Ошибка действия, которая не имеет естественного места в UI («Не удалось сохранить — попробуйте ещё раз»).

Critical-сообщения (квоты, баны, account-conflict) **не используют** тосты — это inline-блоки или отдельные страницы.

## 12. Доступность и копирайтинг

### 12.1. A11y minimum

- Все интерактивы клавиатурой достижимы (Tab, Enter, Escape).
- Все формы с правильно связанными label.
- Все иконки-кнопки с `aria-label`.
- Контраст по WCAG AA (для shadcn-default темы — выполняется из коробки).
- Skip-link «К основному содержимому» в начале страниц с тяжёлым header'ом.

### 12.2. Копирайтинг

- Тон — нейтрально-дружелюбный, обращение на «вы».
- Английские термины, прижившиеся в индустрии (workspace, sandbox, deploy, token, slug), оставляем.
- Сообщения об ошибках — конкретные, без «что-то пошло не так», когда мы знаем что именно. Только generic 500 — расплывчат.
- Кнопки — глаголы первого лица императива («Войти», «Сохранить», «Удалить»), а не существительные («Вход», «Сохранение»).
- Длины: заголовки — до 50 символов, описания пустых состояний — до 100, текст ошибок — одно предложение, до 80 символов идеально.

## 14. Открытые UI-вопросы

1. **Аватары юзеров** — в первой версии только инициалы, без upload? Делать ли upload — дополнительная инфраструктура (хранение картинок, ресайз, CDN). Решение — без upload в v1.
2. **«Добавить участника» при отсутствии invitations UI** — заглушка с подсказкой или вообще скрыть кнопку? Принимаемое значение — заглушка, чтобы юзеры понимали, что фича запланирована.
3. **Тема логин-страницы** — следовать выбранной юзером (light/dark) или принудительно single-mode для бренда? Принимаемое значение — следовать (и публичный сайт, и app единообразны).
4. **Локализация** — UI на русском с самого начала, или двуязычный (RU/EN) с переключателем? В Документе 1 явно нет требования; целевой рынок — РФ. Принимаемое значение — only RU в v1, со структурой текстов, готовой к i18n (тексты в одном месте — `lib/i18n/ru.ts`, без хардкода).
5. **Iframe-публикация preview vs отдельный subdomain** — текущий форк отдаёт превью на `<id>.preview.localhost:8080` через Caddy. Когда у юзера будет много проектов — список карточек с iframe-thumbnails может быть тяжёлым. Возможно, нужно генерировать static screenshot в build-runner и хранить как файл. Это UX-вопрос, не блокирующий MVP — решение откладывается.
6. **Empty state для team-org с одним owner-ом** — как только юзер создал team-org, она пустая. Показывать «пригласите членов» CTA, который ведёт на заглушку, — это плохой UX. Возможно, лучше показать «эта орга пока пустая, ждём приглашений в следующей версии» без CTA. Принимаемое значение — без CTA, с объяснением.

## 15. Резюме

Эта спека описывает **что должно появиться на экранах** для реализации авторизации и multi-tenancy:

- **Auth** — 7 страниц (login, signup, forgot, reset, verify, account-conflict, oauth-error), общий layout.
- **Шелл** — header с org switcher и user-menu, project sidebar, org tabs, email-verification banner.
- **Settings** — профиль (3 страницы), организация (4 страницы), проект (5 страниц).
- **Billing** — overview, лимиты, override-ы, usage history; inline-indicators в опасных зонах.
- **Админка** — опциональный read-only console; CLI/API остаются основным инструментом в v1.
- **Ошибки и пустые** — стандартный набор для 401/403/404/423/402/429/5xx, иллюстрации и конкретные CTA.

UI **не реализует** в v1: приглашения, кастомные домены, реферальный код в форме, Telegram/Max OAuth, выход из чужой орги, смену email юзером, полную админку, редактирование memory.

Вместе с Документом 1 (модель и flows) и Документом 2 (бэкенд) этот документ закрывает требования к первой версии многопользовательского Adorable. Реализация UI идёт **после** Документа 2 (потому что без API ничего не работает) и может вестись параллельно по разделам — auth-pages, project-settings, org-settings, billing — относительно независимы и могут разделиться между разработчиками.
