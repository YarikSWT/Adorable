Design spec · v2.x

Долгоживущие agent-runs
persistent runs + resumable stream

Agent loop выносится из HTTP-хендлера в отдельный воркер. Результат переживает закрытие вкладки, стрим резюмируется, слои масштабируются независимо. Координация — только через Postgres (durable state) и Redis (эфемерный транспорт).

Проблема: loop крутился внутри POST /api/chat Паттерн: persistent runs + event stream + resume Правда: Postgres Код: Gitea
🪶
Центральный инвариант: система не теряет и не портит runs. Любой принятый run приходит к терминальному статусу, транскрипт воспроизводим, наработанный код не теряется — даже при закрытии вкладки, рестарте или смерти воркера.

01 Карта системы

Слева — плоскость исполнения (Browser → Next → очередь → Worker → Reaper). Справа — backing-сервисы. Стрим течёт через Redis, состояние — через Postgres, код — в Gitea. Никакого прямого RPC.

транспорт стрима (Redis) durable state (Postgres) код (Gitea) координация

02 Ключевые архитектурные решения

Каждое — закрытая развилка с осознанным trade-off. Снизу — какую проблему устраняет.

Loop в отдельном воркере pg-boss

Agent loop переезжает из Next.js в долгоживущий Node-процесс. API становится тонким: создать run, поставить в очередь, проксировать стрим.

Персистентность при закрытии вкладки, независимый рестарт, горизонтальное масштабирование.

Готовый транспорт resumable-stream + Redis

Вместо самописного event-log + SSE + reducer — библиотека AI SDK поверх Redis. Воркер publisher, Next subscriber.

Убирает целый класс багов (гонки, порядок, backpressure) — этот код больше не наш.

Fail-fast вместо retry retryLimit: 0

Упавший run не переисполняется. LLM недетерминирована — повтор склеил бы две генерации в один транскрипт.

Durability обеспечивает не retry, а reaper. Транскрипт не портится склейкой.

Server-side bridge для первого хода POST → стрим

POST /api/chat сам подписывается на Redis-стрим воркера и отдаёт его клиенту. useChat получает живой стрим из ответа на send.

Стрим публикуется до гидрации sandbox → bridge цепляется <1с, холодный старт идёт как warmup-парты.

Транскрипт в Postgres UIMessage[] jsonb

Полные UIMessage с tool-parts через onFinish, не плоский текст. Идемпотентность по runId.

Не теряем tool-историю между ходами; на фронт — нативный формат без конверсий.

Reaper застрявших runs heartbeat + CAS

Воркер бьёт heartbeat каждые 10с. Reaper метёт любой не-терминальный статус по таймауту: коммит наработки в draft, терминализация, возврат резерва.

Закрывает осиротевшие runs при hard-crash и не даёт проекту залочиться навсегда.

Liveness ≠ job-expiration

Срок жизни джобы (24h) — грубый потолок, не сигнал живости. Живость определяет только heartbeat.

Устраняет двойное исполнение на границе истечения для реально длинных runs.

1 активный run на проект partial unique index

Уникальный индекс project_id WHERE status NOT terminal вместо racy check-then-insert. Второй POST → unique violation → 409.

Никакого TOCTOU; cancel быстро уводит run в терминал и разблокирует re-enqueue.

Резервация квоты reserve → reconcile

На входе атомарно резервируется оценка под максимум многошагового run-а; в конце recordUsage сверяет факт и возвращает остаток.

Закрывает check-then-act гонку и пере-/недо-биллинг при бёрсте.

Bounded validation feedback

Ошибки билда/типов идут модели как tool-result с эскалацией (3 попытки/категория, дедуп по hash). На исчерпании — модель доигрывает объяснение, без жёсткого abort.

Система сама чинит ошибки за 1–3 итерации без участия юзера.

03 Три хранилища, три роли

Жёсткое разделение ответственности — ключ к простоте восстановления после сбоев.

POSTGRES

Источник правды

  • статус и метаданные run
  • транскрипт messages (UIMessage)
  • activeStreamId, jobId, очередь
  • usage и квоты

Переживает всё. Завершённый run полностью восстановим отсюда.

REDIS

Эфемерный транспорт

  • живые байты UIMessage-стрима (TTL)
  • cancel-флаг cancel:{runId}
  • noeviction — не выселять живой стрим
  • AOF everysec — потеря ≤ 1с

Потеря допустима: reaper доведёт активные runs до failed, завершённые не страдают.

GITEA

Только код

  • main — на успешном run
  • draft/run-* — на cancel / fail / crash
  • meta-репо упразднено
  • sandbox tmpfs жив по idle-TTL 30 мин

Наработка не теряется ни в одной ветке завершения, включая hard-crash (через reaper).

04 Поток: первый ход

Как живой стрим первого сообщения доезжает до браузера через bridge, минуя гонку холодного старта.

POST /api/chat

Резерв квоты → user-сообщение в БД → INSERT run (unique-индекс) → enqueue + сохранить jobId.

Воркер берёт джобу

CAS queued → running, запускает heartbeat (10с) и cancel-poll (5с).

Ранняя публикация стрима

setActiveStream + notifyStreamReady до гидрации. Bridge цепляется за <1с.

Bridge возвращает стрим

POST подписывается через resumeExistingStream и отдаёт байты клиенту. Юзер видит «warming up».

Гидрация + streamText

sandbox + git clone / npm install (warmup-парты) → streamText → toUIMessageStream → дренаж в Redis.

onFinish + финализация

Сохранить UIMessage[] (tool-parts), commit в main, recordUsage, CAS running → completed.

05 Поток: отмена — без дедлока

Развилка по статусу — место, где наивная реализация залочивала бы проект навсегда в статусе cancelling.

Run ещё queued

boss.cancel(jobId)

Снимает джобу — воркер её уже никогда не подберёт.

CAS queued → cancelled

Финализируем сразу в /stop: некому довести cancelling → cancelled.

release + clear

Вернуть резерв квоты, очистить флаги. Проект свободен из unique-индекса.

Run уже running

CAS running → cancelling

Помечаем намерение; воркер довершит сам.

cancel-флаг в Redis

Воркер видит его на следующей итерации loop (≤ 5с) → abort().

Воркер: CAS → cancelled

Сохраняет частичную работу в draft, finalize. Reaper подстрахует при гонке.

06 Поток: смерть воркера → reaper

🌾

Что такое Reaper

Reaper (англ. «жнец», сборщик) — фоновый процесс-санитар. Раз в 30с он сканирует Postgres и подбирает «застрявшие» runs — те, что в не-терминальном статусе, но за которыми уже никто не следит: воркер умер, джоба потерялась, отмена не довершилась.

Он нужен именно потому, что воркер retryLimit: 0 при падении не переисполняется. Без reaper упавший run завис бы в running навсегда, а partial-unique-index залочил бы проект. Reaper — гарант инварианта «любой принятый run придёт к терминальному статусу».

Как находит застрявшихПо heartbeat: живой воркер бьёт heartbeatAt каждые 10с. Старше 60с → осиротел.
Что считается застрявшимrunning (crash) · cancelling (отмена не дошла) · queued с потерянной джобой.
Что делаетCAS→reaping (захват) → draft-commit наработки → терминал → возврат резерва квоты → очистка.
Сколько экземпляровРовно один при scale > 1 — через pg_try_advisory_lock.

Конкретный сценарий — hard-crash (OOM / SIGKILL): finally воркера не выполнится, draft-commit оттуда не произойдёт. Подхватывает reaper — и забирает наработку.

Воркер убит в середине

Heartbeat перестаёт обновляться. Run застрял в running. Sandbox-контейнер ещё жив (idle-TTL 30 мин).

Reaper детектит застревание

tick 30с: status = running и heartbeatAt старше 60с → осиротел.

CAS running → reaping

Эксклюзивный lock на git-операции: живой handler уже не сможет коммитить параллельно.

Draft-commit наработки

Подключается к живому sandbox и коммитит /workspace в draft/run-*. Код не потерян.

reaping → failed + release

Терминализация, возврат резерва квоты, очистка стрима/флага. Проект разблокирован.

07 Машина состояний — источник правды

Все переходы — через finalizeRunCAS(expectStatusIn, …): кто первым сменил статус, тот владелец; остальные — no-op. Нет флипов и двойных операций.

08 Как держится durability

Четыре правила инварианта

  • Все переходы через CAS — кто первый сменил статус, тот владелец; гонок и флипов нет.
  • reaping — эксклюзивный lock на git: пока reaper держит, живой handler уже не закоммитит.
  • Идемпотентность по runId: releaseReservation и recordUsage безопасны при повторе.
  • У каждого не-терминала есть выход — актором или reaper-ом по таймауту. Проект не лочится навсегда.

09 Граница: SDK vs наш код

Принцип — максимум отдать готовому, оставить себе только то, чего в библиотеках нет.

ЗАБРАЛ SDK / RESUMABLE-STREAM
  • batching, порядок, backpressure стрима
  • реконструкция UIMessage с tool-parts (onFinish)
  • resume после reconnect (useChat resume)
  • несколько подписчиков на один стрим
  • рендер UI из стрима — без нашего reducer-а
ОСТАЁТСЯ НАШИМ
  • очередь + воркер (pg-boss) и его durability
  • reaper застрявших runs
  • fail-fast политика и state-machine
  • bounded validation feedback (auto-retry)
  • квоты / usage, stop ↔ pg-boss, commit + draft-ветка

Выкинуто из v1 — самописный транспорт

  • таблица run_events (append-only)
  • event-emitter с batching
  • SSE-эндпоинт с LISTEN/NOTIFY + Last-Event-ID
  • reducer на фронте
  • колонка hasStreamedContent (мёртвая)
  • singletonKey (заменён unique-индексом)

11 Главный оставшийся риск

Не дефект спеки — неизвестность, которую нельзя закрыть на бумаге

Поведение resumable-stream как headless-publisher (воркер публикует без HTTP-клиента) и валидность склейки warmup → llm фрейминга. Корректно изолировано в блокирующем Phase 0 с бинарным исходом и готовым fallback на тонкий Redis Streams pub/sub. Дальше его снимает только код, не дизайн.
